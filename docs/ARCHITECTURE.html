MonitorRisk

SAP S/4HANA RISE Security Scanner — an agentless, offline-first security assessment engine for S/4HANA RISE, ECS, ECC, HANA and BTP. This guide explains how the system is put together, why each boundary sits where it does, and what an engineer must preserve when extending it.

01Architectural thesis

Nearly every structural decision in this codebase falls out of a single commercial and technical reality: in RISE with SAP, you do not own the system you are auditing. You cannot install an agent, you cannot get an RFC user with the authorisations a scanner would want, and third-party ABAP add-ons are an Excluded Task requiring a separate SKU and a multi-week evaluation. A scanner that needs a foothold in the system is a scanner that never gets deployed.

So the product is built the other way round: the customer produces an export, and the scanner is a pure function over that export. Everything else — the module tier, the report engines, the server, the gate — is layered on that one idea. Five invariants hold the design together, and each one is enforced somewhere in code rather than merely intended.

Invariant 1 — The scanner connects to nothing

The analysis engine has no network client of any kind. Connected collection lives in a separate program (collect/) that writes the same files a human would export by hand. The scanner cannot tell which produced them, which is the point: connected mode inherits the offline path's entire test suite for free.

Invariant 2 — A display option may never change a verdict

--severity decides what is listed, not what was found. The FAIR loss figure, the compliance roll-ups, the domain tiles and the release gate all read the unfiltered corpus. Anything that makes a claim about the estate reads the corpus; only rendering reads the filtered list.

Invariant 3 — Missing input is a finding, not a silence

An absent export file loads as None and every dependent check self-skips. Left alone, that produces a clean-looking report over a fraction of the estate. The coverage manifest is computed once per run and carried into every artefact, and it arms the release gate.

Invariant 4 — Never fail open

Degraded coverage is exit code 2 — could not assess, never exit 0. An unreadable gate policy is also 2. A typo in a config file must not quietly disarm a control.

Invariant 5 — A finding must know who can fix it

In RISE, a customer can see a bad profile parameter and cannot change it. Those findings render as a pre-drafted service request to SAP, never as "change this" — and the gate never blocks a developer's build on one.

02System context & trust boundary

Figure 01 is the outermost view. The dashed amber line is the boundary that defines the product: data crosses it outbound only. Nothing is installed inside the SAP estate, no RFC user is created, and nothing is ever written back — in either execution mode.

Two consequences of this shape are worth naming explicitly, because they are usually where competing products differ:

  • Point-in-time, not continuous. The system reads a snapshot. It is a configuration and authorisation assessment, not a monitoring platform. Section 13 explains how the product states that limit on-screen rather than in a footnote.
  • The customer owns the extraction. That is a deployment advantage and an accuracy risk at once, which is why the coverage manifest exists: the scanner must be able to say "you gave me 105 of 123 sources" before it says anything about posture.

03Acquisition tier — three paths, one contract

Three quite different mechanisms produce input, and all three converge on a single in-memory dictionary before any check runs. This convergence is the most load-bearing seam in the system: it is why connected collection required no new tests, and why the ABAP source scanner slots in beside 29 tabular auditors without special-casing the pipeline.

Why collect/ is a separate program

It would have been easier to add a --host flag to the scanner. That option was refused, and the reasoning is worth preserving because it is the product's central claim:

  • Testability. The scanner is a pure function over a directory. Adding a network client to it would mean every audit test now runs against something that can time out.
  • Auditability of the claim. "The scanner connects to nothing" is verifiable by inspection when the scanner contains no client. It is a promise when the client is compiled in and disabled by a flag.
  • Read-only is enforced in the transport, not the caller. The same sapstartsrv service that returns profile parameters also exposes Start, Stop, Restart and OS command execution. The allowlist is checked before the request is constructed — a bug in calling code cannot reach a destructive method.
  • Partial by construction. Users, roles and authorisations are RFC-only, and the RFC route is declined by default (decision D3). Every collect run writes a manifest naming what it could not reach, so partial collection is disclosed rather than silently thin.

04The scanner core pipeline

One pass, seven stages, no hidden state between them. Each stage produces a value the next stage consumes; nothing reaches back. sap_scanner.py is the composition root — it wires the stages together and owns every I/O decision, so the auditors and the report engines can stay pure.

Composition root responsibilities

sap_scanner.py deliberately keeps a handful of concerns that could have been pushed down, because pushing them down would let two components disagree:

ConcernWhy it lives in the composition root
run_ctx constructionBuilt once as {"deployment_mode": …, "modules": set(…)} and passed to every ECS-aware auditor, so two auditors cannot disagree about which estate they are looking at.
Module inter-dependencyiam defers its coarse transaction-level SoD to ara — but only when ara is actually in this run. Passing the module set fixes a real bug where --modules iam stood down in favour of a module that was not running and produced no SoD findings at all.
Corpus vs. display splitThe one place the filtered and unfiltered lists both exist. Every consumer is handed the correct one explicitly.
Coverage manifestComputed once and passed as data to the report tier. A generator's job is to render what it was given, not to import an analysis module.
Output encoding_make_output_encoding_safe() runs before anything else. On Windows, redirecting stdout drops Python to cp1252 and the banner's box-drawing characters raise UnicodeEncodeError before work starts. CI always redirects stdout — a control that cannot run under redirection is not a control.

05Module tier & the finding contract

Thirty auditor classes, each in its own file under modules/, each with a check-ID family it owns exclusively. They share a base class and a uniform entry point, run_all_checks(), returning a list of finding dictionaries. There is no plugin registry and no dynamic discovery: modules are imported and dispatched explicitly in the composition root, which is verbose and makes the run order and the dependency between modules readable in one file.

Two structural details worth knowing before you touch this tier

The constructor signature is not yet uniform. Some auditors take (data, baseline_overrides, run_ctx) positionally; some take (data, baseline_overrides); two take run_context= as a keyword. This is honest history — run_ctx arrived with deployment-mode awareness and was threaded only through the modules that needed it. It is the clearest refactor candidate in the codebase: a single optional third positional parameter on BaseAuditor would let the composition root construct all thirty identically.

Check IDs are partly generated, not all literal. 365 IDs are written as literals; a further 255 are built at runtime, giving 620 once the five runtime-generated families resolve against their shipped rulesets — profile parameters (PARAM-<parameter>, 78 of them), ABAP rules (133), SoD risks and ATC families. That distinction matters when you write tests: you cannot assert a fixed count against a ruleset that ships as data. It matters more than it looks, because anything using the check count as a denominator must resolve all three forms — a keyword check_id=, a positional _emit("AUTH-001", …), and the runtime families — or it is counting failures rather than checks.

Design rule — prefer SAP's own answer

atc_import runs before the in-house ABAP scanner would. Where a customer already licenses SAP's Code Vulnerability Analyzer, those findings are authoritative and produced inside the customer's own system; re-deriving them would only mean disagreeing with SAP about SAP's own tool. The same deference appears between iam and ara: the coarse module stands down when the precise one is running.

06Deployment-mode resolution

This is the part of the design that most distinguishes the product, and it is easy to underrate. The same parameter value can be a critical finding and a mandated baseline, depending on which estate produced the export. SAP Note 3250501 makes specific settings mandatory in Enterprise Cloud Services that are genuine weaknesses on classic on-premise ABAP. A RISE-specific scanner that flags SAP's own baseline is confidently wrong on every compliant system it sees.

The SNC module is a model, not eighteen comparisons

snc_posture is the clearest illustration of a design principle that recurs throughout the check tier: report the problem, not its symptoms. Note 3250501 specifies eighteen SNC and IGS parameters. Evaluated independently, a system with snc/enable = 0 produces ten findings — but every accept_insecure_* setting is moot when SNC is off. Ten findings would report ten problems where the truth is one. The module therefore evaluates the eighteen parameters as a single state model, and additionally checks the relationships the note itself states:

  • igs/snc/name must match snc/identity/as
  • igs/snc/library must match snc/gssapi_lib
  • data_protection/min may not exceed data_protection/max

ecs_config_items covers the configuration half of the same note — the items that are not profile parameters: password-hash tables behind authorisation group SPWD, SSF_PSE_D behind SPSE, unused clients, and audit-log filter coverage. Every one of the note's eighteen items is accounted for in a disposition table naming its owner, so a future note version that adds a nineteenth breaks the build rather than the report. That is the difference between a build-time failure and a silent coverage gap, and it is a pattern worth copying anywhere a shipped ruleset tracks an external standard.

07The corpus split invariant

This deserves its own section because it is the invariant most likely to be broken by a well-meaning change, and because breaking it produces artefacts that are wrong in a way nobody notices.

The rule was introduced narrowly — for the money figure alone, on the argument that a display option must not silently change a dollar amount. The argument was right and its original scope was too small. On --severity HIGH, a compliance category holding real MEDIUM findings rendered the green "no findings" chip: the money was protected and the frameworks were not. The generalised rule is now stated in the code at the split point itself, which is the right place for an invariant that any future consumer of the findings list will need to obey.

Test for any new consumer of the findings list

Ask: does this component show a list, or does it make a claim about the estate? Only the first may take the filtered list. If in doubt, take the corpus — over-counting in a summary is a visible error; under-counting is an invisible one.

08Enrichment & decision chain

Between the raw findings and any artefact sit five independent enrichment components. None of them mutates a finding's identity; each attaches a view of it. They are ordered by dependency, not by importance.

Why FAIR sits here rather than in a module

Quantification is an interpretation of the whole finding set, not a check. Three properties keep it methodologically defensible, and each is a structural choice rather than a disclaimer:

  1. A finding is not a risk. Findings are evidence that shift the FAIR factors of a handful of scoped SAP loss scenarios — internet-facing RCE to ransomware, privileged-access abuse, and so on. The mapping is explicit and the unrouted count is disclosed rather than hidden.
  2. Priced on the unfiltered corpus. The input count is stored beside the figure, so a display filter provably cannot move the number.
  3. No figures, no price. Without the customer's own loss figures (crq_parameters.json or --crq-inputs), the catalogue's illustrative company supplies the shape of the analysis and no currency total is presented as this organisation's exposure — including on the terminal, because a number in scrollback is copied into a chat message exactly as readily as one in a PDF.

09Release gate

--gate is what turns a report into a control. The design is shaped less by what a gate should ideally check than by the four specific ways gates get switched off in practice.

RuleThe failure it prevents
Judge the deltaA gate that fails on the pre-existing backlog is disabled within a week.
Judge only the scopeA developer cannot be asked to fix somebody else's object to ship their own. A scope file naming nothing is refused rather than obeyed — narrowing to nothing would pass every build.
Never block the unfixableIn RISE a ticket_to_sap finding is not the developer's to resolve; failing their build for it teaches them to bypass the gate.
Never fail openDegraded coverage is exit 2. This is why degrades_coverage is a generic flag rather than a hard-coded check ID — an earlier version matched only ABAP-LEX-001, which armed the gate for a mis-lexed file and left it disarmed for an --abap-src typo, a metadata-only export, or unreadable files. A new coverage check now arms the gate the day it is written.
Two sharp edges to know before wiring it up

--gate-write-baseline is evaluated before --gate, so passing both in one command writes the baseline and skips evaluation. And an empty finding set currently returns pass, not "could not assess" — if a run can collapse to zero findings for an unrelated reason, assert on the finding count in the pipeline as well.

10Server tier & persistence

The CLI answers "what is wrong today". The server answers "are we getting better", which is a different question and needs durable state. The two share the scanner core exactly — the server does not re-implement a single check. What it adds is everything that only makes sense across time.

The dependency discipline

The CLI runs on the standard library alone — the HTML, PDF and PPTX engines are all hand-built, with no reportlab and no python-pptx. The server tier deliberately ends that rule, because a browser console and a durable finding store cannot be built on the stdlib. What replaces it is a stated ceiling rather than an absence: a single-digit runtime dependency count (currently four; Jinja2 left when the server-rendered console was replaced by the SPA), no ORM, and no graph database — the graph nodes are rows. The deployment stays one app container plus one PostgreSQL, and the guidance in the repo is explicit that a third service would forfeit the product's clearest structural advantage.

Account recovery as an architectural decision

Worth noting because it is the kind of detail usually left implicit. create-user --generate prints a password to the terminal, so it now lives in shell scrollback and in docker compose logs. The console therefore holds that account at Your account until the password is replaced, and every JSON endpoint stays closed until then. Self-service change requires the current password even though the session is already authenticated — a stolen session should not be enough to take an account over permanently. An admin reset mints a new password rather than setting a chosen one, and either path signs out every other session for that account. Locked out of every admin account, the way back in is from the host, where whoever runs the container already has the database anyway.

11Finding identity & the mitigation journey

Everything the server offers over the CLI rests on one primitive: a finding must be able to recognise itself across runs. Without stable identity, remediation tracking, aging and MTTR are approximations, and a resolved finding that comes back looks like a new one.

12Report tier

Three engines, all pure standard library, all fed the same seven arguments and none of them permitted to compute anything. Each exists because a different reader needs a different artefact, and the shape of each is driven by how that reader will actually use it.

FormatReader & useStructure and what drives it
HTML Interactive triage, at a desk Single self-contained file, logos embedded as data URIs, so it survives being emailed. Overall risk score, P1–P4 queue, severity/category breakdown, compliance panel, live severity filter, collapsible findings each carrying its full risk narrative and remediation.
PDF Formal hand-over to SAP Basis / security Ordered cover → P1–P4 queue → findings by area → compliance mapping → per-finding detail pages. Fix-first order is the whole point: the document is worked through top to bottom. Each detail page names affected objects, the security risk, a numbered remediation procedure and references. Running header/footer, page numbers, confidentiality banner.
PPTX Leadership meeting --pptx-mode full produces a 300+ slide deck with one slide per finding, fix-first, carrying severity and priority chips and exploit tags. --pptx-mode summary produces the short executive deck. Both from a hand-built OOXML engine.
A deliberate asymmetry

The twelve security domains appear on the dashboard, at /domains, as a filter on the triage queue, and as one slide in the deck — but not in the HTML or PDF reports. Those are the long-form hand-over documents and are kept simple. Resist the pull to render every view in every artefact.

The knowledge base

Finding text is not written in the check. Each check emits an identity and its evidence; the narrative lives in data/finding_details.json, keyed by check-id with a family-prefix fallback, and where an entry is absent the report falls back to the finding's own description and remediation. Two consequences: the report is always complete, and improving remediation guidance for 620 checks is a data edit rather than a code change across 30 modules.

13Reach vs. state — the honesty model

This is a product-design decision that turned into an architectural one, and it is the section most worth reading if you are evaluating rather than extending the tool.

The findings are re-expressed in the twelve-domain vocabulary the SAP security market uses, so a reader holding an RFP checklist can match them line for line. The problem: this is an offline, point-in-time configuration assessment, and four of those twelve domains name continuous activities — event monitoring, interface traffic, user behaviour, exploit protection. Twelve tiles each showing a number would assert twelve capabilities, and four of the assertions would be false.

So every domain carries two facts that are easy to confuse, and states both on the tile rather than in a footnote:

FactWhat it answers
ReachWhat this product can ever see in that domain. A property of the product — fixed, identical for every customer.
StateWhat this scan found: findings · no findings · export not supplied · not assessed.

Three reach levels are in use. Fully assessed covers baselining, access and authorisation, identity security, violation management and custom code. Partly assessed covers compliance monitoring (point-in-time, no score), HotNews (a curated subset with its size and cut-off stated), transport security (routes and change control, not payloads) and suspicious user behaviour (a pattern library run retrospectively over the exported log window — not behavioural analytics, not live). Configuration only covers security event monitoring and interface traffic: whether the audit log could have recorded the answer, and which destinations and ACLs exist. Exploit and 0-day protection is not covered at all — it needs a runtime agent and the product holds no connection — so that tile prints a dash, never a zero.

Two structural rules fall out of this

Domain membership is a strict partition: every finding lands in exactly one domain, so the tiles add up to the corpus rather than exceeding it. And findings the vocabulary has no word for — BTP, RISE shared-responsibility, resilience — are listed with the reason rather than dropped. There is no score, no percentage and no maturity rating: the product sees your findings, not your control environment.

14Security posture of the tool itself

A security scanner is a high-value target and handles the most sensitive configuration data an SAP estate produces. The properties below are structural rather than procedural — they hold because of how the system is built, which is the only kind of assurance worth writing down.

PropertyHow it is achieved
No footprint in SAPNothing installed, no add-on transported, no RFC user created, nothing written back. Verifiable by inspection: the scanner contains no network client.
Read-only enforced in transportThe sapstartsrv allowlist is checked before any byte reaches the network, so a caller bug cannot reach Start, Stop, Restart or OS command execution.
No credentials in argvThere is no --password. A credential in argv is visible in ps and in shell history. Prompted, piped, or SAPCONTROL_PASSWORD.
Minimal supply chainCLI: zero runtime dependencies. Server: four, no ORM, no graph database. Every dependency added is a dependency an auditor asks about.
Air-gap capablepython -m server.cli scan runs a full scan with no browser. The whole product functions with no egress.
Authenticated by defaultSeeded admin credentials appear in logs by construction, so the console holds that account until replaced and every JSON endpoint stays closed. The gate is on the data, not the page.
Tamper-evident operationAppend-only audit log; RBAC with per-system row scoping; password change or reset invalidates every other session for that account.
CI-verifiedGitHub Actions runs the full pytest suite on Python 3.8–3.12 plus a full scanner smoke run on every push and pull request.
Handling the output

The artefacts are the sensitive asset. A completed report names privileged users, unlocked standard accounts, exposed services and unpatched HotNews notes — it is an attack plan for the estate it describes. The PDF carries a confidentiality banner for that reason. Treat scan outputs, the export bundle and the PostgreSQL volume at the classification of the SAP system they describe.

15Extending the system

The most common extension is a new audit module. Nine steps, in the order the architecture wants them:

# 1 — declare the input, so absence is a coverage fact rather than silence
modules/data_loader.py     → add filename to FILE_MAP; absent file loads as None
modules/coverage.py        → register the logical source, and whether it is
                             obtainable in RISE at all

# 2 — write the auditor against the base contract
modules/<concern>.py       → class XAuditor(BaseAuditor): run_all_checks()
                             → own a check-ID prefix nothing else uses
                             → self-skip on a missing key; set
                                details.degrades_coverage when you know you
                                could not see everything
                             → take run_ctx if the verdict is deployment-dependent

# 3 — wire it into the composition root
sap_scanner.py             → import, add the --modules key, add to the
                                "all" list, add the dispatch block

# 4 — supply the narrative as data, not code
data/finding_details.json  → risk explanation + numbered remediation per check-id

# 5 — place it in the vocabulary
modules/domains.py         → exactly one domain; the partition must stay strict

# 6 — map it, quantify it, rank it
compliance mapping         → verified control IDs only
fair_adapter               → route to a loss scenario, or accept the unrouted default
risk_prioritizer           → exploitability / exposure signals, if any apply

# 7 — make it testable without an SAP system
sample_data/               → fixtures crafted to trigger every new check

# 8 — prove the contract
tests/                     → module fires · empty input does not crash · field types
                                and severities valid · no check-ID collision · report
                                renders · CLI end-to-end still runs

# 9 — verify the whole pipeline
python -m pytest -q
python sap_scanner.py --data-dir ./sample_data --format all

Where extensions usually go wrong

  • Reading the filtered list. A new summary panel that takes all_findings after the severity filter will silently under-report. Take the corpus (§07).
  • Silent self-skip. A check that skips on missing data without flagging coverage produces a clean-looking result over an estate nobody looked at. Skipping is fine; skipping quietly is not.
  • Hard-coding a coverage signal. Flag it as details.degrades_coverage. Naming a specific check ID in the gate is exactly the bug that was fixed.
  • Computing in the report tier. Generators render what they are given. If a report needs a number, compute it in the composition root and pass it in.
  • Splitting one problem into ten findings. The SNC module exists as a counter-example. Model the state; report the cause.
  • Assuming a fixed check count in tests. Five families are generated at runtime from shipped rulesets.
  • Writing the check ID in a form nothing can read. A positional _emit("X-001", …) and a placeholder-free f"X-001" are both invisible to a naive reader, and a check nothing can enumerate until it fails corrupts any denominator built from the count.

16Known constraints

Stated plainly, because an architecture guide that only lists strengths is a brochure.

ConstraintConsequence & current position
Point-in-time by constructionNo continuous monitoring, no runtime protection, no traffic visibility. The domain model states this on-screen rather than hiding it (§13).
Export quality is the customer'sThe coverage manifest turns this from a hidden risk into a disclosed one, but a thin export still yields a thin assessment.
Users / roles / authorisations are RFC-only in connected modeRFC is declined by default (decision D3), so connected collection is partial by construction and every run writes a manifest naming what it could not reach.
Empty finding set returns passThe gate treats zero findings as exit 0, not "could not assess". Assert on finding count in the pipeline until this closes.
Non-uniform auditor constructorsThree signature shapes across 30 modules (§05). Cosmetic today; it will bite when run_ctx gains a field every module needs.
HotNews catalogue is curatedA verified subset of high-impact Notes since 2020, not the full SAP Note corpus. Size and cut-off are stated; extensible via sap_security_notes.json.
Custom-code scanning needs an abapGit exportThe cva module cannot run without --abap-src. Where SAP's own CVA is licensed, atc ingests those results instead and is preferred.
Per-category denominators are a floorThe check-id → category map reads literals only, so per-category rates in the trend view are computed against fewer checks than actually ran. The per-module counts used by the posture score resolve all three ID forms; the category map does not yet.
